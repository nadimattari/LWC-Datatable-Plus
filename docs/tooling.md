## Formatting

JavaScript, HTML, CSS, JSON, Markdown, Apex classes, and Apex triggers are formatted with Prettier using a gofmt-inspired configuration: tabs for indentation, tab width 4, no semicolons, single quotes, no trailing commas, no bracket padding, and a print width of 100. Apex still requires statement semicolons because the language parser requires them. Salesforce XML manifests are generated by the CLI and are not passed through Prettier. Local editor settings in `.vscode/` are excluded because they are not source artifacts.

Sources:

- https://prettier.io/docs/en/options.html
- https://github.com/dangmai/prettier-plugin-apex#configuration

## Lightning Web Component testing

LWC unit tests run through `@salesforce/sfdx-lwc-jest`, which supplies the Jest preset, LWC transformer, resolver, serializer, and base component stubs. The default config is imported into `jest.config.js` and extended with test-path exclusions and an 80% global coverage threshold. The coverage glob is overridden to `force-app/main/default/lwc/**/*.js` because the extensionless default from the preset collected no files in this project, producing an empty 0% report that silently bypassed the threshold.

Source:

## Service-boundary implementation

The Apex query service applies the verified patterns above. Object and field names are resolved through schema describes before they enter dynamic SOQL, field accessibility is checked from the describe results, and queries run with `AccessLevel.USER_MODE` from a read-only `@AuraEnabled(cacheable=true)` method. Search text is supplied through `Database.queryWithBinds` bind variables. The request, response, and error DTOs are top-level classes with `@AuraEnabled` properties. Expected failures are returned in the envelope with documented error codes; unexpected exceptions are logged without client details.

## Query-controls implementation

The query controls use `lightning-input type="search"` with a required `label`, `onchange` for each value change, and `oncommit` for a finished edit such as Enter. Search requests are delayed with `setTimeout`; each new value clears and restarts the timer, and disconnection clears any pending timer. `lightning-button` supplies labelled, keyboard-reachable first, previous, next, and last controls; `disabled` communicates boundary state to assistive technology. The page status uses `aria-live="polite"` so assistive technology can announce page changes.

Internal `searchrequest` and `pagerequest` events use `CustomEvent` with a fresh `detail` object. Their names are lowercase and do not start with `on`. They bubble to the immediate parent but do not cross the shadow boundary because only the owning shell handles them.

The LWC lint rule `no-async-operation` is suppressed only at the debounce timer. The rule guidance targets DOM timing that belongs in lifecycle hooks; user-input debouncing needs a cancellable timer, which this component clears on commit and disconnect.

## Shell implementation

The shell calls the imperative Apex method from `connectedCallback()`, which the lifecycle reference documents as the hook for initialization and data fetching. Initial state, loading, and error markup use the current `lwc:if` / `lwc:elseif` / `lwc:else` directives; the older `if:true` and `if:false` directives are explicitly no longer recommended. The platform datatable receives `data`, `columns`, a case-sensitive `key-field`, `aria-label`, and `is-loading`; its reference documents that `isLoading` shows a spinner. The queried field list is the ordered, de-duplicated union of `keyField` and each column's `fieldName` so the renderer always receives its row key.

A single empty `role="status"` element remains in the DOM and its text changes for loading, loaded, and empty results. MDN states that `aria-live` is set on an empty element and updated later, and that content added after the initial accessibility tree is built may be missed; the component therefore does not conditionally create its status region. Inline query failures still use `role="alert"` because the failure is dynamic and requires immediate attention; the ARIA reference describes it as an assertive live region that should be added to the message node. Tests mock the imported Apex method at the module boundary with `jest.mock()` and configure promise results with `mockResolvedValue` / `mockRejectedValue`, following the official mock-function guidance. The component is exposed for App, Home, and Record pages through `isExposed` and `<targets>`; configuration properties use only the supported `String` and `Integer` types, while array properties are supplied by a wrapping component. The required `objectApiName` property is marked `required="true"` in target configuration, which the target reference defines as an admin-facing Boolean attribute whose default is `false`.

## Interaction wiring

The shell listens for the internal `searchrequest` and `pagerequest` events and passes the active query state back to the controls. Platform datatable sort events supply `detail.fieldName` and `detail.sortDirection` with values `asc` or `desc`; the shell normalizes the direction through the shared request helper before calling Apex. A sort event without an `ASC` or `DESC` direction clears both sort values so the service never receives a half-specified sort. Row-selection events supply `detail.selectedRows`, which is the authoritative current selection, and `selected-rows` preselects rows by key value. The shell derives `selectedRowKeys` from the key field and clears both arrays after each query result to honor the page-scoped selection decision. `refresh()` is decorated with `@api` because public methods are part of a component's API, and it starts a new imperative Apex invocation using the current request object. A monotonically increasing request identity discards late responses from superseded requests.

## V1 verification

Final verification ran on 2026-11-22 against the `dtp-dev` validation org at API 68.0 with the explicit CLI path required by this environment. `npm run verify` passed end to end: formatter and lint clean; 81 LWC tests with 100% statements, functions, and lines and 99.14% branches; deploy validation with 26 of 26 local Apex tests successful; deployment succeeded; and 26 Apex tests passed with 93% org-wide coverage. The Jest cache was cleared before final coverage collection so every component module was included in the report.

The component-style usage guide added on 2026-11-23 was verified with the same gate and produced the same results. The guide also records the `sortable: true` column requirement clarified in the API contract.

`npm audit --audit-level=high` passed. The dependency tree reports low and moderate advisories in development tooling whose fixes require breaking major-version changes; no high or critical advisory blocks V1. Secret, naming, suppression, skipped-test, and stub scans found no added violations.

The keyboard pass is Jest-rendered: the internal controls are asserted as a labelled search input and four labelled page buttons with correct disabled boundary states. The shell keeps one polite status region in the DOM and uses an alert only for query failures.

Manual in-org render gap: row rendering is verified through Jest-rendered tests and the metadata deploy gate, but no manual visual check of a populated table was performed inside `dtp-dev`. Restricted-user gap: the authenticated `dtp-dev` user has the System Administrator profile, so object and field accessibility was not exercised as a restricted user. The Apex service still checks `isAccessible()` for the object and every requested field and runs both count and row queries with `AccessLevel.USER_MODE`. A restricted-user smoke check remains required before production use.

V1 was deployed only to the validation org; no production rollout or feature flag was used. Rollback is metadata-only: revert the V1 metadata and documentation commits from `main`, then redeploy the pre-V1 source from `736b08f`. No schema migration, data backfill, or external integration is included in V1.
